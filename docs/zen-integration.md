# Интеграция atlas с пространствами и группами вкладок Zen (design, не реализация)

Вопрос: «подумай (не реализуй) — как интегрировать atlas с пространствами и группами
вкладок zen браузера». Дата: 2026-10-08. Метод: только read-only — исходники atlas и
`~/Projects/ai/zen-tabs`, живые файлы `~/.zen` (через `bin/spaces.mjs --json`), `curl`
на локальные порты, `systemctl --user`, `zen-browser --help`, `hyprctl clients -j`,
`sqlite3 -readonly` на control.db. Изменений в коде нет.

## Вердикт

Единственная здравая форма интеграции — нативная панель «Zen» в atlas, которая едет
на уже существующем мосте пользователя: CLI-скрипты `zen-tabs` (`spaces.mjs`,
`session.mjs`) как источник инвентаря и его же службы `:8093`/`:8096` как живой канал;
второй мост не изобретать. Данные уже текут — `import_zen()` (importers.rs:587) гоняет
`spaces.mjs --json`, но выбрасывает поле `groups`, а вид поиска `zen_tab` существует
только как подпись во фронте (static/app.js:1489) без импортёра: закрыть оба пробела —
и список пространств/групп/вкладок с поиском получается почти даром. Живую видимость
«что открыто сейчас» из файлов сессии не получить честно (отставание наблюдали 22 мин
при живом браузере) — для неё расширение должно публиковать вкладки активного
пространства на локальную службу симметрично `plan.json`, только в обратную сторону.
Любые действия (открыть URL, сфокусировать вкладку, собрать группу) — только через
расширение и только в активном пространстве: `moveTabToWorkspace` в Zen привилегирован.
Запись в файлы живого профиля запрещена — их владелец Firefox/Zen, перезапишет или
побьёт. Итог двумя этапами: Stage 1 — инвентарь + поиск + фокус окна (S-M), Stage 2 —
канал расширение→atlas для live-списка и открытия URL (M-L).

## Что уже есть (свидетельства)

**atlas.** `import_zen()` запускает `bun …/zen-tabs/bin/spaces.mjs --json` (cfg.rs:71-77)
с таймаутом 45 с и берёт из ответа только `name`, `tabs`, `idleDays→lastAccessed`,
`uuid` — `groups`, `icon`, `domains` и по-вкладочный состав выбрасываются. Результат
едет в панель sources (источник `zen`, бейдж `Z`) и в сопоставление
`projects.zen_space` через `zen_space_for` (сейчас совпал один проект:
«Игры» → «игры и геймдев»). Синк — по `POST /api/sync` (http.rs:1035). Поиск:
в control.db ровно четыре вида (`memory_fact` 3078, `vault_note` 371, `omp_session` 27,
`board_item` 3) — `zen_tab` в выдаче не участвует, хотя слот с подписью «вкладка» и
голубым цветом в KIND_LABELS/KIND_CYAN давно готов.

**zen-tabs** (`~/Projects/ai/zen-tabs`, README исчерпывающий). Расширение MV2
`zen-tabs@local` (permissions: `tabs`, `tabGroups`, `storage`, хосты 8091/8093/8096)
видит **только вкладки активного пространства** — «Zen отдаёт расширению вкладки только
активного пространства, а сменить вкладке пространство можно лишь внутренним
(привилегированным) `moveTabToWorkspace`» (README, «Ограничения»). Умеет: `tabs.create`
(в текущее пространство), `tabs.remove`, `tabs.move`, `tabs.group` + `tabGroups.update`
(заголовок/цвет), `storage.local`. Службы (systemd --user, обе живые):
`:8093` — `serve-plan.py`, отдаёт `~/.cache/zen-tabs/plan.json` с CORS и `no-store`
(план от 2026-09-24: 681 вкладка, 675 переносов — сам по себе пример протухания);
`:8096` — `serve-ctl.py`: `GET /status` (модели + VRAM) и POST-действия с фиксированным
списком и защитой `X-Zen-Tabs: 1` — preflight пропустит только origin `moz-extension://`.

**Файлы профиля** (`~/.zen/dtdhrwbn.Default (release)-1/`): `zen-sessions.jsonlz4`
(собственный стор Zen: пространства, группы, вкладки) и
`sessionstore-backups/recovery.jsonlz4` (классический sessionstore). На момент
проверки (18:56) оба имели mtime 18:34 при запущенном браузере — отставание 22 мин.

**Браузер** (zen-browser-bin 1.22.2b-1, firefox-ветка). `zen-browser --help`:
`--new-tab <url>` открывает в **последнее активное** окно/пространство — выбора
пространства нет; удалённое управление — `--start-debugger-server` (RDP, порт 6000),
`--marionette` (2828) и `--remote-debugging-port` — цитата: «Start the Firefox Remote
Agent, which is a low-level remote debugging interface used for **WebDriver BiDi**» —
то есть **не CDP**, Puppeteer/Playwright напрямую не подходят, и все три требуют
запуска браузера с флагом. Ничего из этого сейчас не слушается (`ss`; то же
подтверждено в docs/embeddable-apps.md). Окно Zen в Hyprland — класс `zen`, **один
клиент на все 624 вкладки**: скрытые вкладки других пространств отдельными окнами не
видны, заголовок окна = активная вкладка. Установка расширения временная
(Load Temporary Add-on): в `extensions.json` запись есть, xpi в `extensions/` — нет,
живёт до перезапуска браузера.

## Матрица возможностей

| Действие | Статус | Механизм | Оценка |
|---|---|---|---|
| Список пространств и групп | возможно сегодня | `spaces.mjs --json` уже отдаёт и то и другое; atlas не читает `groups` | S |
| Поиск по открытым вкладкам | возможно сегодня | индексировать `zen_tab` из `zen-sessions.jsonlz4` батчем в sync; слот UI готов | S-M |
| Фокус: окно браузера | возможно сегодня | `/api/focus` план со степом `hyprctl dispatch focuswindow class:zen` | S |
| Видимость «что открыто сейчас» live | нужно расширение | файл сессии отстаёт; расширение публикует вкладки активного пространства на `:8096` | M |
| Перейти/сфокусировать вкладку | нужно расширение | `tabs.update(id, {active})` — только вкладка активного пространства; смена пространства извне невозможна (привилегированный API) | M |
| Открыть URL в нужном пространстве | нужно расширение | только в активное: `tabs.create`; в неактивное — очередь переносов как режим B, автоматом никак | M |
| Создать/переименовать группу, цвет | нужно расширение | `tabs.group` + `tabGroups.update` в активном пространстве | M |
| Перенести вкладку между пространствами | невозможно (WebExtension) | `moveTabToWorkspace` привилегирован; единственный путь — Zen Mod (см. «НЕ делаем») | — |

## Два этапа

**Stage 1 — инвентарь и поиск, read-only + фокус окна (S-M).**
1. `importers.rs`: не выбрасывать `groups`/`icon` из ответа `spaces.mjs`; persist в
   control.db (например `zen_spaces(uuid, name, icon, tabs, last_accessed)` +
   `zen_groups(space_uuid, name)`), чтобы панель не пересчитывала на каждый рендер.
2. Новый вид доков `zen_tab`: по-вкладочный срез из `zen-sessions.jsonlz4` — title, url,
   пространство, группа, lastAccessed. Два пути, брать второй: (а) парсить mozlz4 в Rust
   (`lz4_flex`, формат тривиален — 8 байт магии + uint32 + LZ4-блок, см. session.mjs);
   (б) вызывать `bin/session.mjs --json` тем же паттерном, что `import_zen` гоняет
   `spaces.mjs` — ноль нового Rust-кода, минус: поле `space` в sessionstore лежит как
   `tab.zenWorkspace`-uuid, маппинг на имена должен дать `spaces.mjs`. Обновление — в
   существующий `sync_search_docs` по `/api/sync`; `source_ref` = URL вкладки.
3. Панель «Zen»: дерево пространство → группы → вкладки, счётчики и «простой» (данные
   уже в ответе), клик по вкладке — `POST /api/focus` (фокус окна; про саму вкладку —
   честная приписка «активное пространство»).
4. Статус моста в sources: `GET :8096/status` и свежесть `plan.json` (`:8093`) как
   health источника `zen` — «статус расширения — в нативную панель (класс B)», как уже
   решено в embeddable-apps.md.

**Stage 2 — действия через расширение (M-L).**
1. Live-канал: в `serve-ctl.py` добавить `POST /tabs` с той же защитой, что у действий
   (заголовок `X-Zen-Tabs: 1` → preflight пропустит только расширение; у расширения
   host-permission на 8096 уже есть). Расширение раз в N секунд публикует `tabs.query`
   активного пространства (код `loadTabs()` уже есть); atlas читает `GET :8096/tabs`.
   Писец один — расширение; atlas только читает.
2. Обратные команды: очередь в той же службе (`GET /commands`, идемпотентные id) —
   atlas кладёт «открыть URL», «активировать вкладку», «сгруппировать», расширение
   забирает и исполняет через `tabs.create/update/group`. Atlas никогда не дергает
   браузер сам — только ставит в очередь.
3. «Открыть в пространстве X»: если X активно — сразу; иначе положить в очередь и
   подсказать переключить пространство вручную (это ровно режим B zen-tabs: очередь
   переносов руками, и он осознанно так устроен, потому что иначе нельзя).
4. Постоянная установка расширения (подпись AMO или `xpinstall.signatures.required=false`
   в about:config) — иначе весь Stage 2 умирает с каждым перезапуском браузера.

## Свежесть данных и риски

- **Отставание sessionstore.** Запись event-driven: наблюдали 22 мин при живом
  браузере; `recovery.baklz4` отстаёт от `recovery.jsonlz4` ещё ~15 с (доки Mozilla).
  Для инвентаря и поиска — нормально; для «реального времени» — нет, отсюда Stage 2.
- **Живой профиль не трогаем.** Никаких записей в `~/.zen` пока Zen запущен: файлы
  принадлежат браузеру, он их периодически перезаписывает — конкурентная запись =
  битая сессия. Все мутации — только через API браузера (расширение).
- **Приватность.** `zen_tab` в `search_docs` — это заголовки ~600 вкладок (youtube,
  github, финансы, здоровье) в поисковом индексе на диске, попадающие в выдачу по
  векторной ноге. Дешёвая страховка: индексировать title+url (контента и нет),
  добавить exclude-список пространств (OTHER — первый кандидат).
- **Один писатель.** Боль plan.json (руками `--write` + пересборка xpi) — урок: у
  каждого артефакта ровно один писец. В новой схеме: файлы сессии пишет Zen, `/tabs` и
  `/commands` — расширение через ctl, atlas — только читатель и постановщик очереди.
- **Временное расширение.** До постоянной установки live-канал — best effort: браузер
  перезапустили — канала нет, Stage 1 при этом продолжает работать по файлам.

## Что осознанно НЕ делаем

- **Встраивать окно браузера в atlas** — закрыто Wayland на уровне протокола
  (docs/term-embed.md, путь А); embeddable-apps.md уже записал Zen в класс B
  («вкладки браузера — не панель контрольного центра»).
- **Гнать UI браузера синтетически** (wlrctl/xdotool-клики по вкладкам): хрупко,
  ломается о любой редизайн, и всё, что им делается, делается честнее через расширение.
- **Дублировать мост**: вторая служба, второй формат плана, свой парсер плана в atlas —
  нет; ездим на zen-tabs и его же защите (preflight-заголовок, фиксированные действия).
- **Zen Mod с привилегированным доступом** (`gZenWorkspaces.moveTabToWorkspace`,
  переключение пространств; система модов официальная, прецедент — ergozen):
  технически это единственный путь к кросс-пространственным действиям, но это
  сопровождение привилегированного chrome-JS под каждую версию Zen — за пределами
  обоих этапов; вернуться, только если очередь переносов руками перестанет устраивать.
