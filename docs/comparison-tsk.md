# tsk (smarzban/tsk) vs atlas

## Вердикт

**Код — нет, интероп — формально да, но незачем; идеи — да.** tsk — терминальная доска задач «для тебя и твоих агентов» (Rust TUI + CLI, MIT, v0.11.6, 190★, создан 2026-08, push за часы до проверки): ни код, ни хранилище (JSON-файлы в `~/.tsk` против нашего SQLite), ни поверхность (TUI против девяти GUI-панелей) atlas не переиспользуют. Формально интероп возможен без единой строчки в atlas — tsk-клиент запускается в herdr-сессии панели «Терминал» (плагину нужен herdr ≥0.9.0, стоит 0.9.3), но это вторая доска рядом с существующей. Его «coming soon» — назначить задачу агенту и гонять в herdr worktrees — это ровно то, что у нас уже делает оркестратор. Реальная ценность — идеи: полноценный машинный CLI к нашей доске (сегодня агентам доступны только `atlas notify`, HTTP и чат), шаги-чеклисты у дела, дисциплина именованных ошибок.

## Профиль tsk

- Rust, MIT, v0.11.6; 190★, 8 форков, 13 issues; активно развивается (push 2026-10-09).
- Хранилище: `~/.tsk/tsk.json` + ротация бэкапов + `trash.jsonl` (корзина 30 дней, undo на доске); не БД; формат v5, миграции.
- Доска: статусы `open→ready→started→blocked→review→done`; проекты выводятся из git-cwd (+ «desk» без git); треды; шаги-чеклисты; заметки.
- CLI агентов: `add/list/status/steps/edit/archive --json`, JSON-планы пачкой, дедупликация по заголовку, именованные отказы (`unknown-project`), документированный exit-контракт; `tsk setup omp|pi|claude|…` ставит скилл.
- herdr-плагин: доска сплит-панелью + quick capture (`prefix+t` / `prefix+a`).
- Нет: вложений, графа зависимостей, поиска, источников/синков, оркестратора, уведомлений, PTY, make-раннера, патруля, настроек на окно, GUI.

## Пересечение с atlas

| tsk | atlas | Вывод |
|---|---|---|
| Доска задач, 6 статусов | Доска Эйзенхауэра: квадранты, done, описание, вложения | Разные роли: очередь работ vs личная триаж-доска |
| Проекты из git-cwd + архив проектов | Реестр проектов + архив + источники (herdr/git/vault) | Пересечение; наш реестр шире и явный |
| Агентский CLI (`tsk add/status --json`) | `atlas notify` + HTTP API доски + оркестратор-чат | У tsk машинный интерфейс заметно полнее |
| herdr-плагин (доска внутри клиента) | herdr-панель, H/T-фокус, клиент в «Терминале» | Разные уровни: контент внутри herdr vs управление herdr |
| Шаги-чеклисты задачи | Описание + вложения | Чеклистов как сущности у нас нет |
| — | Граф зависимостей, гибридный поиск, Orchestrator rpc (approvals/history), patrol, make-раннер, кольцо уведомлений, Terminal PTY, настройки окон | Только у atlas |

## Что позаимствовать (по убыванию ценности)

1. **S/M — агентский CLI к доске**: `atlas board add|list|status --json` — тонкий HTTP-клиент в ветке CLI рядом с `notify` (src-tauri, `main.rs`). Агент двигает дела без чата и curl; паттерн tsk — идемпотентные команды, именованные отказы, стабильный JSON, задокументированные коды выхода.
2. **S/M — шаги-чеклисты дела**: `steps` в `board_items` + расширение PATCH `/api/board/item/{id}`; в карточке UI — чекбоксы. Для агентских задач список шагов ценнее простыни описания — tsk это доказывает.
3. **S — exit-контракт как стандарт для всех CLI-команд atlas**: каждый отказ именован, повтор безопасен, вывод стабилен; один абзац в README + проверка в `atlas notify`/`board`.

Честно: больше брать нечего — undo/корзина дублируются нашим `done`-флагом, git-cwd-скоупинг противоречит явной модели проектов, TUI-полировка в Tauri не переносится.

## Что у tsk лучше

- Машинная поверхность: `--json` везде, идемпотентность, именованные ошибки, скилл-инсталлер — агент работает с доской без чтения исходников; у atlas это только HTTP и чат.
- Нулевая настройка: зашёл в git-каталог — доска уже на его проекте; atlas требует, чтобы проект существовал в реестре.
- Семантика статусов под агентов (`review` = «сделал агент — ждёт тебя») — готовый словарь для нашей доски и оркестратора.
